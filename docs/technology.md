# 기술성 평가 기준 및 구현 구조

기술성은 대상 특허가 기존 기술과 비교해 어떤 기술적 차이를 가지는지와, 그 기술이 특허 문헌에 실제 구현 가능한 수준으로 설명되어 있는지를 평가한다.

```text
기술성 점수(100)
= 기술 차별성(50)
+ 구현 구체성(50)
```

기술성은 법적 신규성·진보성, 권리범위, 시장 성장성, 매출 가능성 또는 실제 제품 적용 여부를 평가하지 않는다.

## 1. 기술 차별성 (50점)

### 비교 재료

- 대상 특허 독립항 및 주요 종속항
- 해결과제, 해결수단, 발명의 효과
- 상세설명과 도면의 처리 흐름
- 선행기술조사문헌의 대표 청구항, 초록, 해결수단, 상세설명
- CPC 또는 IPC 기반 유사 특허의 대표 청구항, 초록, 해결수단, 상세설명

선행기술조사문헌을 우선 비교군으로 사용하고, 부족한 비교군은 embedding similarity 기반 유사 특허로 보완한다. 점수는 비교군의 개수가 아니라 대상 특허의 핵심 해결수단과 가장 가까운 비교문헌을 기준으로 선택한다.

### 비교 절차

1. 대상 특허에서 해결과제, 핵심 구성, 역할·입출력·상호관계, 처리 단계, 판단 조건, 데이터 흐름 및 제어 방식을 추출한다.
2. 비교문헌에서도 동일한 비교 단위를 추출한다.
3. 목적이나 명칭이 아니라 핵심 해결수단의 구조와 작동 원리가 가장 가까운 문헌을 식별한다.
4. 공통점과 차이점을 같은 단위끼리 대조한다.
5. 차이가 핵심 해결수단을 변경하는지, 보조 단계·조건·파라미터 수준인지 구분한다.
6. 차이에서 기술적 효과가 직접 발생하는지와 동일 효과를 대체 구현하는 데 필요한 기술 작업을 판단한다.

### 점수 기준

#### 구성·동작 방식 차별성 (25점)

| 점수 | 기준 |
| ---: | --- |
| 25 | 가장 가까운 비교문헌과 핵심 구성 또는 결합 관계가 다르고, 처리 순서·판단 로직·데이터 흐름·제어 방식이 별도의 작동 원리를 형성한다. 해당 차이를 제거하면 대상 특허의 핵심 결과나 작동 방식을 유지하기 어렵다. |
| 17 | 기반 구성이나 목적은 일부 공통이지만 핵심 구성의 조합·역할 배치 또는 주요 처리 단계에 차이가 있으며, 해당 차이가 최종 출력이나 핵심 작동 방식에 실질적으로 영향을 준다. |
| 8 | 독립항의 주요 구성과 전체 흐름이 비교문헌에 대부분 존재하며, 차이는 보완 기능, 전후처리, 적용 대상, 임계값, 파라미터 또는 예외 조건 수준이다. |
| 0 | 비교문헌이 핵심 구성과 주요 처리 흐름을 대부분 포함하거나, 대상·비교문헌 자료가 부족해 차이를 판단할 수 없다. |

#### 기술 효과 차별성 (15점)

| 점수 | 기준 |
| ---: | --- |
| 15 | 핵심 구성·동작 차이에서 비교문헌에 없는 별도 기술 효과가 직접 발생하며, 차이와 효과의 인과관계가 문헌에서 구체적으로 확인된다. |
| 10 | 전체 효과 방향은 일부 유사하지만 핵심 구성 또는 처리 차이로 별도 효과가 추가되고 연결관계가 확인된다. |
| 5 | 효과의 종류와 발생 원리가 대체로 같고 차이는 성능 정도, 처리 범위, 적용 조건 또는 일반적 개선 표현 수준이다. |
| 0 | 비교문헌이 주요 효과와 발생 원리를 대부분 포함하거나, 구성·동작과 효과의 연결 근거가 부족하다. |

#### 모방·회피 난이도 (10점)

이 항목은 법적 회피설계나 침해 성립이 아니라 동일하거나 유사한 효과를 다른 기술 구조로 재현하는 데 필요한 기술적 노력만 평가한다.

| 점수 | 기준 |
| ---: | --- |
| 10 | 동일 효과를 위해 여러 핵심 구성의 정밀한 결합, 상호 의존 단계, 전문 알고리즘 또는 특수 제어 조건이 함께 필요하며 통상적 대체로 효과를 유지하기 어렵다. |
| 7 | 일부 구성은 대체할 수 있지만 동일 수준의 효과를 안정적으로 구현하려면 처리 흐름 재설계, 파라미터 조정, 예외 처리 또는 복수 구성 최적화가 필요하다. |
| 3 | 구성 간 의존성이 낮아 통상적 모듈·알고리즘·데이터 처리 방식의 일부 수정으로 유사 효과를 구현할 수 있다. |
| 0 | 일반적인 구성 연결이나 알려진 모듈의 단순 조합으로 효과를 쉽게 재현할 수 있거나 판단 자료가 부족하다. |

## 2. 구현 구체성 (50점)

구현 구체성은 비교문헌이 아니라 대상 특허 자체의 청구항, 상세설명, 도면 및 실시예를 평가한다. 구성이나 단계의 명칭이 존재한다는 이유만으로 고득점하지 않는다.

### 구성 요소 구체성 (20점)

확인 대상은 구성요소의 명칭, 역할, 입력, 처리 결과, 출력 및 다른 구성과의 연결·호출·의존 관계다.

| 점수 | 기준 |
| ---: | --- |
| 20 | 핵심 구성별 역할·입력·출력·상호관계가 확인되고, 청구항의 핵심 구성이 상세설명이나 도면의 실제 구조와 연결된다. |
| 14 | 주요 구성과 기본 역할은 확인되지만 일부 입력·출력, 호출 관계, 데이터 전달 방식 또는 연결 조건에 추가 설계가 필요하다. |
| 7 | 구성 명칭이나 기능은 있으나 내부 역할·입출력·상호작용이 추상적이어서 구체적 결합 구조를 설계하기 어렵다. |
| 0 | 핵심 구성을 식별하기 어렵거나 기능적 결과만 제시된다. |

### 처리 절차 구체성 (20점)

확인 대상은 시작 조건, 단계별 입력과 처리, 판단 조건, 분기·반복, 데이터 변환·전달, 출력 및 제어 흐름이다.

| 점수 | 기준 |
| ---: | --- |
| 20 | 시작부터 최종 출력까지 입력·처리·판단·분기·데이터 변환·출력·제어 흐름이 설명되고 청구항·상세설명·도면 단계가 대응된다. |
| 14 | 주요 단계와 순서는 확인되지만 일부 입출력, 조건 분기, 반복 조건, 예외 처리 또는 데이터 전달 관계가 제한적이다. |
| 7 | 전체 순서만 개략적으로 제시되고 단계별 데이터, 수행 내용, 판단 기준 또는 생성 결과가 불명확하다. |
| 0 | 기능이나 최종 결과만 제시되고 단계별 처리 흐름을 확인하기 어렵다. |

### 구현 설명 및 기술적 활용 가능성 (10점)

| 점수 | 기준 |
| ---: | --- |
| 10 | 실시예·도면·산식·파라미터·데이터 구조·제어 조건·변형 예시 중 복수 자료가 실제 내용과 함께 제공되고 적용 구조를 설계할 수 있다. |
| 7 | 적용 대상과 기본 구현 방향 및 참고자료는 확인되지만 일부 파라미터, 데이터 구조, 제어 조건, 예외 상황 또는 변형 예시가 부족하다. |
| 3 | 적용 분야나 목적만 제시되고 구현 설명이 기능적·포괄적이어서 알고리즘, 인터페이스 또는 제어 조건을 상당 부분 추가 설계해야 한다. |
| 0 | 실시예나 구현 참고정보가 없어 실제 적용 방식을 판단하기 어렵다. |

## 3. 입력 및 출력 구조

기술성 입력은 `valuation_inputs/technology_input.json`에 저장된다. 주요 입력은 다음과 같다.

- `patent.claim_context`
- `patent.technical_context`
- `technology_metrics.representative_cpc`
- `technology_metrics.representative_ipc`
- `technology_metrics.similar_patents`
- `technology_metrics.target_document_indicators`
- `technology_metrics.warnings`
- `citation_evidence`
- `prior_art_candidates`

기술성 결과는 `valuation.axes.technology`에 저장된다.

```json
{
  "score": 0,
  "subscores": {
    "technical_differentiation": {
      "score": 0,
      "max_score": 50,
      "details": {
        "configuration_operation_differentiation": {},
        "effect_differentiation": {},
        "imitation_avoidance_difficulty": {}
      }
    },
    "implementation_specificity": {
      "score": 0,
      "max_score": 50,
      "details": {
        "component_specificity": {},
        "procedure_specificity": {},
        "implementation_utilization_specificity": {}
      }
    }
  }
}
```

각 상세 근거 객체에는 다음 정보가 포함된다.

- 평가 상태
- 대상 특허 근거
- 비교문헌 근거
- 공통점과 차이점
- 선택 점수 이유
- 부족 정보
- 효과 인과관계 또는 대체 구현에 필요한 기술 작업

## 4. Supervisor 검증

기술성 Supervisor는 다음 항목을 규칙 기반으로 확인한다.

- 세부지표별 허용 점수 사용 여부
- 세부점수, 하위점수 및 기술성 총점의 합계 일치 여부
- 대상 특허와 비교문헌 근거 존재 여부
- 점수 이유가 구체적인지 여부
- 자료 부족 상태와 점수의 일관성
- 최고점과 누락·불명확·추가 설계 근거의 모순 여부

검증에 실패하면 기술성 축만 `valuation_retry` 대상으로 지정한다.

## 5. Final Report 반영

Final report에는 기술성 총점과 등급만 표시하고 세부지표별 점수는 표시하지 않는다. 다만 내부 상세 근거를 사용해 다음 내용을 설명한다.

- 기존 방식과의 공통점 및 차이
- 차별적 해결수단과 기술 효과
- 모방·대체 구현 관점
- 구현 구조와 처리 절차
- 유지 판단에 주는 기술적 의미

확인 사항은 역할별로 분리한다.

- 사업부: 현재 활용 여부, 향후 활용 계획, 대체 기술, 비용 대비 유지 실익
- 법무팀: 선행문헌 대비 청구항 차이, 보호범위, 포트폴리오·해외 권리
- 기술 검토: 구현 파라미터, 인터페이스, 성능 재현 조건, 대체 구현 가능성

## 6. 실행 방법

전체 workflow:

```bash
.venv/bin/python -m app.main P201702001-KR0
```

기술성 단독 평가:

```bash
.venv/bin/python scripts/evaluate_technology_only.py P201702001-KR0
```

단독 평가 결과:

```text
artifacts/runs/manual/technology_only_<timestamp>_<management_number>/
├── technology_eval_result.json
└── technology_eval_report.md
```
